## Cart and Wishlist (Phase 4)

- Livewire class components: `app/Livewire/CartManager.php` rendered by `/cart` and
  `app/Livewire/Wishlist.php` rendered by `/wishlist` (`routes/web.php`, both under
  `auth`, route names `cart` and `wishlist`).
- `CartItem::mergeAdd()` (`app/Models/CartItem.php`) is the single merge point for adds
  from the product page and the wishlist: the same SKU stays one row (FR-26) and the
  quantity is capped at `min(30, stock)` (FR-27).
- CartManager seeds typed quantity bindings on mount and clamps every edit through
  `setQty()`: below 1 lands on 1, above 30 or above stock clips with the explanatory
  message "Quantity clipped to {N}: only {S} left in stock." or "Quantity clipped to
  {N}, the per-SKU limit is 30." (FR-27); sold-out rows refuse edits outright.
- The subtotal and per-row totals re-render live from the typed binding
  (`wire:model.live="quantities.{{ $item->id }}"` + `updatedQuantities` hook) with no
  page load (FR-28). Rows whose stock shrank while parked are flagged ("Stock changed:
  only {S} left") and rows sold out show the remove hint (FR-29 flagging in the cart;
  the checkout-time block lands in Phase 5).
- Wishlist: saved products are product-level, not tied to an SKU
  (`app/Livewire/Wishlist.php`); move-to-cart takes the product's first variant with
  stock, merges through `mergeAdd`, then removes the save (FR-30). Products out of
  stock everywhere or no longer active stay saved with a notice.
- Header nav (`resources/views/layouts/app.blade.php`) links Catalog, Cart (with the
  summed quantity), and Wishlist for signed-in accounts; the product page confirms an
  add with "Added to cart: {label}.".
- Tests: `tests/Feature/CartManagerTest.php` (12) and `tests/Feature/WishlistTest.php`
  (6) cover FR-25..FR-31 flows and the three Key Test Criteria of section 5.4;
  `productWithVariants()` moved to `tests/Pest.php` as a shared helper.

## Checkout and Orders (Phase 5)

- `CheckoutForm` (`app/Livewire/CheckoutForm.php`) requires authentication, guides
  customers with an empty cart back to the catalog, supports pickup or courier
  delivery, validates the courier address, and previews the configured flat fee
  and optional note.
- `OrderService` (`app/Services/OrderService.php`) locks cart rows and SKU rows
  in a stable order, rechecks live stock, snapshots prices and variant labels,
  reserves stock, stores courier addresses, and clears the cart atomically.
- Customer order pages are scoped to the signed-in customer; cancellation is
  pending-only and restores reserved stock once. Tests cover stale-stock rollback,
  totals, order codes, ownership, and cancellation (`tests/Feature/CheckoutTest.php`,
  `tests/Feature/OrdersTest.php`).

## Midtrans Payment and Expiry (Phase 6)

- `MidtransPaymentService` creates a Snap transaction over Laravel's HTTP client,
  enables bank transfer, GoPay, QRIS, and card, applies the configurable expiry,
  and stores one payment per order. Checkout redirects directly to the trusted
  Midtrans-hosted payment URL; orders with a failed session can retry from the
  order page.
- `POST /api/midtrans/callback` verifies SHA-512 signatures, stores valid webhook
  payloads, reconfirms status and amount with Midtrans, and returns HTTP 200 for
  invalid or failed notifications. Confirmed settlement/capture finalizes stock;
  deny/cancel/expiry releases it idempotently.
- Order details provide a server-side status check and show payment state/expiry.
  `midtrans:expire-pending` is scheduled every five minutes to expire overdue
  provider transactions and release stock for orders whose Snap request failed.
- Payment configuration is read from the existing `MIDTRANS_*` environment
  variables; no SDK or database schema changes were added.
- Tests: `tests/Feature/MidtransPaymentTest.php` covers Snap redirect and payload,
  signature rejection, idempotent settlement, failure/cancellation, status checks,
  and expiry. Admin order details expose stored failure context and pending orders
  without a recorded payment session (FR-47).

## Order Lifecycle and Admin Panel (Phase 7)

- `app/Livewire/Admin/Dashboard.php` shows settled payments for the current day,
  open-order counts, and the oldest orders awaiting action.
- `app/Livewire/Admin/Catalog/{Categories,Products/Form,Products/Index}.php`
  manages category and product data, unique category slugs and SKUs, publication
  with at least one SKU, and non-negative stock adjustments. Products and SKUs
  referenced by carts or order history cannot be deleted.
- `app/Livewire/Admin/AdminOrderManager.php` lists and filters orders, shows
  customer, item, address, payment, and cancellation details, and enforces the
  order transitions. Courier orders need a waybill before shipping; pickup orders
  become ready for collection; customers confirm receipt before either delivery
  path completes.
- `app/Services/OrderService.php` locks order and inventory rows during lifecycle
  changes, returns reserved stock once on cancellation, and stores the required
  admin note. Admin cancellation stops before shipping; pending Midtrans payments
  are cancelled and reconfirmed before stock is released. The admin screen does
  not claim to issue a provider refund.
- The additive migration
  `database/migrations/2026_10_27_000001_add_admin_operations_fields_to_orders_and_shipping_addresses.php`
  stores `orders.refund_note` and `shipping_addresses.waybill_number`, as approved.
- `app/Livewire/Admin/SalesReport.php` reports settled, non-cancelled order totals
  by payment settlement date over a validated date range.
- `app/Livewire/Admin/AdminAccounts.php` and the `admin.accounts` super-admin-only
  route manage admin accounts without exposing super-admin role changes.
- The admin navigation is shared in `resources/views/components/admin-nav.blade.php`;

- Tests: `tests/Feature/AdminCatalogTest.php`,

## Real-time Chat (Phase 8)

- `app/Services/ChatService.php` owns the chat rules of PRD 5.9: one open
  session per customer, reused on every visit, with the linked order attached
  when the chat is opened from an order page (FR-58). Messages are trimmed
  plain text of at most 2000 characters, the visible history is the last 50
  lines oldest-first, the unread counters are per sender side, and the header
  badge counts unread admin lines across all sessions (FR-59, FR-62).
- Sending is a row-locked transaction: a closed session refuses any further
  line, and the first admin reply claims `admin_id` on the session so two
  admins cannot claim at once (FR-61). Only admins may close a session; the
  closed history stays readable and the customer can start a new conversation
  (FR-63). Messages are text only — every path validates the 2000-character
  limit and no upload UI exists (FR-64).
- `routes/channels.php` guards the `chat.{sessionId}` private channel: the
  owning customer plus any admin until an admin claims the session, then only
  that admin. Broadcast pushes use `ShouldBroadcastNow` events
  (`ChatMessageSent`, `ChatRead`, `ChatSessionClosed`) with `broadcastAs`
  names `message.received`, `message.read`, and `session.closed`; a failed
  push is logged and never removes a stored message.
- `app/Livewire/CustomerChat.php` renders one conversation with the context
  order link, `app/Livewire/ChatButton.php` shows the header unread badge on
  every page, and `app/Livewire/Admin/AdminChatPanel.php` lists open sessions
  with previews and unread badges for the team. The navigation adds the chat
  entry points (`routes/web.php`: `chat`, `admin.chat`;
  `resources/views/layouts/app.blade.php`,
  `resources/views/components/admin-nav.blade.php`), and the order page links
  "Open the chat" with the order as context.
- `resources/js/app.js` boots Laravel Echo over Reverb and relays channel
  events into the Livewire components as browser events
  (`chat.message.received`, `chat.read.updated`, `chat.session.closed`), so
  both sides update live without a reload (FR-60, FR-62).
- Tests: `tests/Feature/ChatTest.php` (13 tests) covers session reuse, order
  linking, message limits, the 50-line history, admin claiming, read states,
  the unread badge, closure rules, fresh sessions, and channel authorization.
  The full suite stands at 123 tests / 538 assertions.
- Running the chat for real requires `php artisan reverb:start` besides the
  web server; tests authenticate channels over HTTP and do not need it.

## Non-Functional Hardening (Phase 9)

Audited PRD section 6 requirement by requirement and closed every gap the
application itself owns:

- Security: `Register` now rate-limits sign-ups too — 5 attempts per 600 s
  keyed by caller IP (`app/Livewire/Auth/Register.php`), thrown before
  validation, with no clear on success so mass account creation stays capped;
  the blocked attempt reports under `email` as "Too many registration
  attempts. Try again in {N} seconds." Login already had its limiter (FR-03).
  HTTPS is enforced only in production
  (`app/Providers/AppServiceProvider.php`: `URL::forceScheme('https')`), so
  local development stays plain HTTP while deployed URLs always upgrade.
- SEO: `resources/views/layouts/app.blade.php` yields `meta_description`;
  Livewire shows that component-view `@section` values propagate into the
  layout's `@yield`, so `product-detail.blade.php` sets the per-product title
  and description and `catalog-page.blade.php` does it for home and category
  pages (`CatalogPage::activeCategoryName()`); `ProductDetail::structuredData()`
  emits schema.org Product JSON-LD with an AggregateOffer of per-SKU offers
  (SKU, IDR price, InStock/OutOfStock), rendered with the JSON_HEX_* flags so
  content cannot break out of the script tag. All other pages already carried
  `#[Title]` attributes.
- Observability: every lifecycle change in `OrderService`
  (cancel, adminCancel, ready for pickup, ship, receipt confirm) now leaves
  one structured `Log::info('An order status was updated.')` line with
  order code, action, status, and refund note; the webhook logs an info line
  per accepted notification (`app/Http/Controllers/WebhookController.php`).
  Log files switched from single to daily with 30-day retention
  (`.env`/`.env.example`: `LOG_STACK=daily`, `LOG_DAILY_DAYS=30`).
- Availability and backup: new `db:backup` command
  (`app/Console/Commands/BackupDatabase.php`) runs `pg_dump -Fc` through
  the Process facade, writes `storage/app/private/backups/backup-*.dump`
  (the `local` disk root is `storage/app/private`), prunes dumps older than
  `--keep-days=14`, and logs success/failure; scheduled daily at 01:00
  with `withoutOverlapping` (`routes/console.php`). The recovery procedure
  was executed for real: dump the local database, `createdb` a scratch
  database, `pg_restore` into it, verify (20 tables, the 3 seeded accounts,
  8 products), then drop the scratch database. Documented in the README.
- Payment safety, privacy, compatibility, and accessibility were verified in
  place from the earlier phases: the server key is read server-side only, the
  webhook always verifies the signature and logs hold no card data, checkout
  stores courier addresses only, account deletion is manual per super admin,
  and the restyled views carry AA contrast, focus styles, labels, and
  keyboard-operable navigation. Performance (LCP ≤ 2.5 s p75, filters
  < 200 ms p50) is a documented production target: the catalog pages run
  a bounded query set with 24-per-page pagination, and v1.0 ships no
  runtime profiler.
- Tests: `tests/Feature/HardeningTest.php` (4 tests) covers the sign-up cap,
  the product-page title/description/JSON-LD, the catalog title/description,
  and the structured transition log. The full suite stands at 127 tests /
  556 assertions.
- `README.md` was rewritten from skeleton boilerplate into a project readme:
  stack, setup, demo accounts, running processes (`reverb:start`,
  `schedule:work`), scheduled jobs, backup + tested recovery, operating
  notes, and the tracker pointer.
